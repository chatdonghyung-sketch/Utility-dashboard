## 1. 프로젝트 개요

### 1.1 목적
반도체/제조 공장의 설비 유지보수 데이터를 중앙 집중형 웹 대시보드로 통합 관리한다.  
기존에 엑셀로 분산 관리되던 운전일지·에너지 사용량·작업 지시서·HMI 트렌드 데이터를  
단일 SQLite 기반 웹 애플리케이션으로 통합하여 실시간 조회·입력·분석이 가능하도록 한다.

### 1.2 시스템 명칭
- 정식 명칭: **Maintenance Data Dashboard (MDD)**
- 부제: SQLite 로컬 배포 버전

### 1.3 배포 형태
- 사내 단독 PC 또는 로컬 서버에 설치하여 사용하는 **로컬 웹 애플리케이션**
- 별도의 클라우드 또는 외부 서버 없이 `start.py` 실행 한 번으로 서비스 기동
- 브라우저에서 `http://localhost:5000` 접속

## 4. 데이터베이스 설계

### 4.1 사용 DB
- **SQLite** (파일: `mdd_data.db`, 앱 기동 시 자동 생성)
- 비동기 엔진: `aiosqlite` + `SQLAlchemy asyncio`

### 4.2 테이블 정의

#### 4.2.1 chiller_log — 냉동기·냉각탑 운전일지

| 컬럼 | 타입 | 설명 |
|------|------|------|
| year | INTEGER | 연도 |
| month | INTEGER | 월 |
| day | INTEGER | 일 |
| equipment_id | TEXT | 설비 식별자 (예: CH-01) |
| param_key | TEXT | 파라미터 키 (예: inlet_temp) |
| value | TEXT | 측정값 |

- PK: `(year, month, day, equipment_id, param_key)`
- UPSERT: 동일 PK 존재 시 value 덮어쓰기

#### 4.2.2 chiller_inspector — 냉동기 점검자

| 컬럼 | 타입 | 설명 |
|------|------|------|
| year | INTEGER | 연도 |
| month | INTEGER | 월 |
| day | INTEGER | 일 |
| name | TEXT | 점검자 이름 |

- PK: `(year, month, day)`

#### 4.2.3 chiller_analysis — 냉동기 가동 분석

| 컬럼 | 타입 | 설명 |
|------|------|------|
| year | INTEGER | 연도 |
| month | INTEGER | 월 |
| day | INTEGER | 일 |
| chiller_id | TEXT | 냉동기 ID |
| value | TEXT | 분석값 |

- PK: `(year, month, day, chiller_id)`

#### 4.2.4 ffu_log / boiler_log / safety_log — 일별 운전·점검일지

세 테이블은 동일 스키마를 공유한다.

| 컬럼 | 타입 | 설명 |
|------|------|------|
| date | TEXT | 날짜 (YYYY-MM-DD) |
| field_key | TEXT | 필드 식별자 |
| value | TEXT | 입력값 |

- PK: `(date, field_key)`
- FFU: Fan Filter Unit 운전일지
- Boiler: 보일러 운전일지
- Safety: 안전 점검일지

#### 4.2.5 work_orders — 작업 지시서

| 컬럼 | 타입 | 설명 |
|------|------|------|
| wo_no | TEXT | WO 번호 (PK) |
| work_type | TEXT | 작업 유형 |
| work_name | TEXT | 작업명 |
| equip_code | TEXT | 설비코드 |
| equip_name | TEXT | 설비명 |
| equip_type | TEXT | 설비종류 |
| location | TEXT | 위치 L4 |
| start_date | TEXT | 시작일 (YYYY-MM-DD) |
| end_date | TEXT | 종료일 (YYYY-MM-DD) |
| department | TEXT | 작업부서 |
| worker | TEXT | 작업자 |
| writer | TEXT | 작성자 |
| wo_status | TEXT | WO 상태 (원문) |
| wo_status_normalized | TEXT | WO 상태 (공백 제거 정규화) |

- 인덱스: `idx_wo_start(start_date)`, `idx_wo_dept(department)`, `idx_wo_status(wo_status_normalized)`
- WO 상태 정규화: 공백 제거 후 저장 (예: "작성 중" → "작성중")

## 5. API 명세

### 5.1 냉동기·냉각탑 운전일지

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | `/api/chiller-log` | 월별 전체 데이터 조회 |
| POST | `/api/chiller-log/cell` | 단일 셀 저장 |
| POST | `/api/chiller-log/bulk` | 월 전체 일괄 저장 |

**GET /api/chiller-log**
- Query: `year` (int), `month` (int)
- Response: `{ "YYYY-MM__DAY__EQUIP_ID__PARAM_KEY": "value", ... }`

**POST /api/chiller-log/cell**
```json
{
  "year": 2026, "month": 4, "day": 14,
  "equipment_id": "CH-01", "param_key": "inlet_temp", "value": "7.5"
}
```
점검자 저장 시: `"type": "inspector"`, `"value": "홍길동"` 포함

**POST /api/chiller-log/bulk**
```json
{
  "year": 2026, "month": 4,
  "cells": [{"day":1, "equipment_id":"CH-01", "param_key":"inlet_temp", "value":"7.2"}],
  "inspectors": [{"day":1, "name":"홍길동"}]
}
```

---

### 5.2 냉동기 가동 분석

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | `/api/chiller-analysis` | 월별 분석 데이터 조회 |
| POST | `/api/chiller-analysis/cell` | 단일 셀 저장 |
| POST | `/api/chiller-analysis/bulk` | 일괄 저장 |

---

### 5.3 일별 운전·점검일지 (FFU / Boiler / Safety)

세 모듈은 동일 패턴의 엔드포인트를 공유한다.

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | `/api/{module}-log` | 특정 날짜 데이터 조회 |
| POST | `/api/{module}-log/cell` | 단일 필드 저장 |
| POST | `/api/{module}-log/bulk` | 일괄 저장 |

**GET Query**: `date=YYYY-MM-DD`

---

### 5.4 HMI 트렌드

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | `/api/trend/dates` | 사용 가능한 날짜 목록 |
| GET | `/api/trend/filters` | FAB → Process 필터 구조 |
| GET | `/api/trend/data` | 단일 날짜 24시간 시계열 |
| GET | `/api/trend/range` | 날짜 범위 일별 집계 |

**GET /api/trend/data**
- Query: `date` (YYYYMMDD), `fab`, `process`
- Response: 태그별 `{ tag, unit, alarm_high, alarm_low, max[], avg[], min[] }` 배열

**GET /api/trend/range**
- Query: `start_date`, `end_date`, `fab`, `process`
- Response: `{ dates: [...], tags: [...] }` — 일최대/일평균/일최소 집계

**XLS 파일 구조** (`TREND_YYYYMMDD.xls`, 시트명: `Raw Data`)

| 컬럼 인덱스 | 내용 |
|------------|------|
| 1 | FAB |
| 2 | Process |
| 3 | Tag 명칭 |
| 4 | 값 유형 (MAX / AVG / MIN) |
| 5–28 | 시간별 값 (24시간) |
| 29 | 단위 |
| 30 | 알람값 (MAX→상한, MIN→하한) |

---

### 5.5 작업 지시서

| 메서드 | 경로 | 설명 |
|--------|------|------|
| POST | `/api/work-orders/upload` | 엑셀 파일 업로드 및 UPSERT |
| GET | `/api/work-orders` | 목록 조회 (필터·페이징) |
| GET | `/api/work-orders/kpi` | KPI 집계 (상태별 건수) |
| GET | `/api/work-orders/filter-options` | 필터 선택지 목록 |

**POST /api/work-orders/upload**
- Content-Type: `multipart/form-data`
- 헤더 행 자동 탐색 (`Wo No` 열 기준)
- UPSERT: WO No 기준 중복 시 전체 필드 업데이트

**GET /api/work-orders Query 파라미터**

| 파라미터 | 설명 |
|----------|------|
| start_date | 시작일 필터 (YYYY-MM-DD) |
| end_date | 종료일 필터 |
| department | 작업부서 |
| wo_status | WO 상태 |
| work_type | 작업 유형 |
| equip_type | 설비종류 |
| location | 위치 |
| worker | 작업자 (부분 일치) |
| page | 페이지 번호 (기본 1) |
| page_size | 페이지당 건수 (기본 50) |

**GET /api/work-orders/kpi Response**
```json
{
  "confirmed": 120,
  "drafting":  30,
  "pending":   10,
  "total":     165,
  "other":     5
}
```

### 5.6 에너지 사용량

| 메서드 | 경로 | 설명 |
|--------|------|------|
| GET | `/api/energy-files` | 전체 유틸리티·공장별 일별 사용량 |

- Query: `refresh=true` 로 캐시 강제 갱신 (기본 5분 TTL)
- 디렉토리 자동 스캔: `LNG / STEAM / NItrogen / ARGON` × `1공장 / 2공장 / 3공장 / 신공장`
- 날짜 파싱: 폴더명 `YY년 M월` 또는 파일명 내 `YYYYMMDD` 패턴

**Response 구조**
```json
{
  "gas":      { "f1": [{"date":"2026-04-01","value":1234.5}], "f2": [], "f3": [], "fnew": [] },
  "steam":    { "f1": [], ... },
  "nitrogen": { "f1": [], ... },
  "argon":    { "f1": [], ... }
}
```

**엑셀 파일 구조** (`Energy Management Item(Day) List_YYYYMMDD.xlsx`)

| 행 | A열 | B열 |
|----|-----|-----|
| 5행~ | 일(1~31) | 일별 사용량 |

## 6. 실행 방법

### 6.1 사전 요구사항
- Python 3.10 이상 설치
- 인터넷 연결 (최초 패키지 설치 시)

### 6.2 실행

```bash
python start.py
```

1. `requirements.txt` 기반 패키지 자동 설치
2. uvicorn으로 FastAPI 서버 기동 (`0.0.0.0:5000`)
3. 브라우저에서 `http://localhost:5000` 접속

### 6.3 데이터 업데이트 절차

#### 에너지 사용량 업데이트
1. 해당 유틸리티 폴더(`LNG/`, `STEAM/`, `NItrogen/`, `ARGON/`)의 공장 하위 폴더에 새 엑셀 파일 복사
2. 파일명에 날짜 포함 필수 (예: `Energy Management Item(Day) List_20260514.xlsx`)
3. 앱 재시작 또는 `/api/energy-files?refresh=true` 호출로 반영

#### HMI 트렌드 업데이트
1. `HMI_Trend_data/` 폴더에 `TREND_YYYYMMDD.xls` 파일 추가

#### 작업 지시서 업데이트
1. 웹 UI에서 새 엑셀 파일 업로드 또는
2. 파일을 `Work_Order/` 폴더에 복사 후 업로드

## 7. 버전 관리 정책

### 7.1 Semantic Versioning
- **MAJOR**: 호환되지 않는 API 변경, DB 스키마 대규모 변경
- **MINOR**: 새 기능 추가 (하위 호환 유지)
- **PATCH**: 버그 수정, 데이터·문서 업데이트

### 7.2 버전 관리 파일
- `VERSION` — 현재 버전 단일 소스
- `CHANGELOG.md` — 버전별 변경 이력
- GitHub 이슈 — 각 버전의 zip 파일 첨부 보관

### 7.3 새 버전 배포 절차
1. 변경사항 개발 및 테스트
2. `VERSION` 파일 버전 번호 업데이트
3. `CHANGELOG.md` 변경사항 기록
4. git commit & push
5. GitHub 이슈에 새 zip 파일 첨부

## 9. 알려진 제약사항

| 항목 | 내용 |

| 동시 접속 | SQLite 특성상 다수 동시 쓰기 시 성능 저하 가능. 소규모(~10명) 환경 권장 |
