## 1. 기획 배경

### 1.1 현행 업무 환경

반도체 및 제조 공장의 기계설비팀은 냉동기, 냉각탑, 보일러, 공조기, 펌프, 팬 등 다수의 유틸리티 설비를 24시간 운영함. 설비 운영 과정에서 운전일지, 점검일지, 에너지 사용량, HMI 트렌드, 작업 지시서 등 다양한 운영 데이터가 지속적으로 발생함.

그러나 현행 데이터 관리는 담당자별 개인 PC와 개별 엑셀 파일 중심으로 이루어지는 구조임. 데이터가 설비별, 담당자별, 업무별로 분산되어 있어 통합 조회가 어렵고, 과거 이력 확인과 작업 현황 파악에 많은 시간이 소요됨.

### 1.2 문제 정의

현재 업무 방식의 주요 문제는 다음과 같음.

| 구분 | 문제 | 상세 내용 |
|------|------|-----------|
| 데이터 관리 | 데이터 분산 | 운전일지, 에너지 사용량, 작업 지시서, HMI 트렌드가 서로 다른 파일과 PC에 저장됨 |
| 이력 관리 | 과거 이력 추적 어려움 | 담당자 교체 또는 파일 위치 변경 시 과거 데이터 인수인계 누락 가능성 존재 |
| 현황 파악 | 실시간 조회 한계 | 현장 방문, 전화 확인, 엑셀 파일 열람 없이는 현재 설비 상태 파악이 어려움 |
| 에너지 관리 | 분석 체계 부족 | LNG, 스팀, 질소, 아르곤 사용량이 월말 집계 중심으로 관리되어 추이 분석이 제한됨 |
| 작업 관리 | Work Order 관리 비효율 | 수천 건의 작업 지시서를 엑셀 필터로 조회하여 KPI 집계와 상태 파악에 수작업 발생 |
| 이상 대응 | 대응 지연 | 설비 이상 발생 시 데이터 확인과 원인 추적에 시간이 소요되어 초기 대응이 지연될 수 있음 |

### 1.3 기획 필요성

설비 운영 데이터는 단순 기록물이 아니라 설비 상태 판단, 예방정비 계획 수립, 에너지 비용 관리, 작업 우선순위 결정의 근거 자료임. 따라서 분산된 엑셀 파일을 통합하고, 주요 데이터를 웹 화면에서 즉시 조회할 수 있는 구조가 필요함.

MDD는 별도 클라우드 서버 없이 사내 PC에서 실행 가능한 로컬 배포형 대시보드로 기획함. 이를 통해 보안 제약이 있는 제조 현장에서도 기존 파일 기반 업무를 유지하면서 데이터 통합 관리 체계를 구축하는 것을 목표로 함.

## 2. 기획 목적

### 2.1 핵심 목표

MDD의 핵심 목표는 기계설비 운영 데이터를 하나의 웹 화면에서 입력, 조회, 분석, 집계할 수 있는 통합 관리 환경을 구축하는 것임.

### 2.2 세부 목표

| 목표 | 내용 |
|------|------|
| 데이터 통합 | 운전일지, 점검일지, 작업 지시서, 에너지 사용량, HMI 트렌드 데이터를 단일 시스템에서 관리함 |
| 업무 효율화 | 엑셀 파일 조회, 수작업 집계, 중복 입력을 줄이고 웹 기반 입력·조회 구조로 전환함 |
| 현황 가시화 | 설비 상태, 작업 현황, 에너지 사용량, 알람 정보를 대시보드에서 직관적으로 확인함 |
| 이력 관리 | SQLite DB를 활용하여 운전일지와 작업 지시서 이력을 누적 관리함 |
| 비용 관리 | 유틸리티별·공장별 에너지 사용량을 집계하여 비용 관리의 기초 데이터를 확보함 |
| 확장 기반 확보 | 향후 PostgreSQL 전환, 예지보전, 이상 탐지, 자동 보고서 기능으로 확장 가능한 구조를 마련함 |

## 3. 시스템 기획 방향

### 3.1 기본 방향

MDD는 현장 적용성과 운영 편의성을 우선하는 로컬 웹 애플리케이션으로 기획함. 대규모 시스템 구축보다 빠른 PoC와 실무 검증을 우선하며, 기존 엑셀 파일을 완전히 대체하기보다 엑셀 기반 데이터를 웹 시스템으로 흡수하는 구조를 적용함.

### 3.2 설계 원칙

- 현장 담당자가 별도 교육 없이 사용할 수 있는 단순한 화면 구성 지향
- 기존 엑셀 데이터 형식과 폴더 구조를 최대한 유지하는 방식 적용
- 웹 UI 입력 데이터는 SQLite DB에 저장하여 이력 관리 가능하도록 설계
- HMI 및 에너지 사용량 데이터는 원본 파일을 기반으로 조회하여 초기 도입 부담 최소화
- `python start.py` 실행만으로 서비스가 기동되는 간편 배포 구조 적용
- 향후 사내 서버 또는 PostgreSQL 전환 가능성을 고려한 모듈형 구조 지향

- 사용자별 로그인 및 권한 관리

- 모바일 전용 화면 최적화
- 자동 보고서 PDF 생성

위 기능은 초기 운영 안정화 이후 후속 버전에서 검토함.

## 5. 주요 기능 기획

### 5.1 메인 대시보드

메인 대시보드는 설비 운영 현황을 한 화면에서 파악하기 위한 진입 화면으로 기획함. 설비 총 수, 전체 가동률, 알람 등급별 건수, 이번 달 작업 현황, 최근 이상 알림을 주요 KPI 카드와 차트로 표시함.

기획 의도는 담당자가 여러 엑셀 파일을 열지 않아도 현재 설비와 작업 상태를 빠르게 확인할 수 있도록 하는 것임.

### 5.2 실시간 모니터링

실시간 모니터링 기능은 설비 상태를 정상, 주의, 위험 등급으로 구분하여 표시하는 기능으로 기획함. 설비별 상세 데이터를 조회하고, 알람 발생 시 확인·조치·완료 상태를 추적할 수 있도록 구성함.

단, 초기 버전에서는 실제 센서 실시간 연동보다 화면 구조와 데이터 표시 체계 검증을 우선함.

### 5.3 냉동기·냉각탑 운전일지

냉동기·냉각탑 운전일지는 월별 설비 파라미터를 웹 UI에서 입력하고 SQLite DB에 저장하는 기능임. 냉동기, 냉각탑, 냉수 펌프, 냉각수 펌프 등 주요 설비의 온도, 압력, 전류, 운전 상태 값을 관리함.

단일 셀 저장과 월 전체 일괄 저장 기능을 제공하여 사용자가 엑셀과 유사한 방식으로 데이터를 입력할 수 있도록 기획함.

### 5.4 냉동기 가동 분석

냉동기 가동 분석 기능은 냉동기별 가동 상태, 가동 시간, 전류, RT 등 분석 데이터를 월별로 관리하기 위한 기능임. 운전일지 데이터와 별도 테이블로 관리하여 분석 목적의 데이터를 독립적으로 누적함.

향후 설비별 효율 비교, 이상 징후 탐지, 정비 우선순위 판단에 활용 가능한 기초 데이터 확보를 목적으로 함.

### 5.5 FFU·보일러·안전 점검일지

FFU, 보일러, 안전 점검일지는 일별 점검 데이터를 동일한 구조로 입력·저장하는 기능임. 각 모듈은 날짜와 필드 키를 기준으로 데이터를 관리하며, 동일한 API 패턴을 적용함.

이를 통해 점검 양식은 다르지만 저장 구조는 통일하여 개발과 유지보수의 복잡도를 낮추는 것을 목표로 함.

### 5.6 HMI 트렌드

HMI 트렌드 기능은 HMI 시스템에서 추출한 `TREND_YYYYMMDD.xls` 파일을 기준으로 FAB, Process, Tag별 데이터를 조회하는 기능임. 단일 날짜 기준 24시간 MAX, AVG, MIN 데이터를 제공하고, 기간 조회 시 일최대, 일평균, 일최소 집계 데이터를 제공함.

기획 의도는 별도 HMI 시스템에 접속하지 않고도 설비 주요 태그의 추이와 알람 기준을 웹 화면에서 확인할 수 있도록 하는 것임.

### 5.7 에너지 사용량

에너지 사용량 기능은 LNG, STEAM, NItrogen, ARGON 사용량을 공장별로 조회하는 기능임. 유틸리티별 폴더와 공장별 하위 폴더를 자동 스캔하여 일별 사용량을 집계함.

월 사용량, 누적 사용량, 공장별 비교, 에너지원별 비중 분석의 기반 기능으로 기획함. 초기 버전에서는 사용량 조회와 시각화를 우선하며, 예산 대비 집행률과 초과 알림은 후속 개선 항목으로 검토함.

### 5.8 작업 지시서

작업 지시서 기능은 엑셀 파일을 업로드하여 Work Order 데이터를 DB에 적재하고, 기간, 부서, 작업 유형, 설비 종류, 위치, 작업자, 상태 기준으로 조회하는 기능임.

WO No를 기준으로 중복 데이터를 갱신하는 UPSERT 구조를 적용함. 이를 통해 수천 건의 작업 지시서를 엑셀 필터에 의존하지 않고 웹 화면에서 조회하고, 상태별 KPI를 자동 집계할 수 있도록 기획함.

### 5.9 AI 분석·예지 기능

AI 분석·예지 기능은 향후 확장 방향으로 기획함. 설비 센서 데이터 기반 이상 패턴 감지, 진동·압력·온도·차압·유량 편차 분석, 예방정비 권장사항 제공을 목표로 함.

초기 버전에서는 실제 AI 모델 운영보다 예지보전 화면 구조와 분석 항목 정의를 우선함. 향후 데이터 누적 후 모델 적용 가능성을 검토함.

### 5.10 클린룸 환경 모니터링

클린룸 환경 모니터링 기능은 온도, 습도, 차압, 파티클 등 클린룸 환경 데이터를 화면에서 확인하기 위한 기능으로 기획함. 위험, 주의, 정상 등급으로 룸 상태를 구분하고, 공기조화 프로세스 측정 포인트를 조회할 수 있도록 구성함.

초기 버전에서는 실제 센서 연동보다 화면 설계와 데이터 구조 검증을 우선함.

|------|-----------|---------|-----------|

### 6.2 비용 관리 효과

- 유틸리티 사용량 추이 확인을 통한 에너지 과다 사용 조기 인지 가능함
- 설비별 운전 이력 축적을 통한 비효율 설비 식별 가능함
- 예방정비 기반 데이터 확보를 통해 긴급 고장 및 부품 교체 비용 절감 가능함
- 작업 지시서 상태 분석을 통해 정비 인력과 작업 우선순위 조정 가능함

### 6.3 품질 및 안전 효과

- 점검일지 디지털화를 통한 점검 누락 가능성 감소
- HMI 트렌드 확인을 통한 설비 이상 징후 조기 파악 가능함
- 클린룸 환경 데이터 조회 기반 공정 품질 리스크 관리 가능함
- 알람 및 점검 이력 축적을 통한 반복 고장 원인 분석 가능함

### 6.4 의사결정 지원 효과

- 월별·연도별 에너지 사용량 분석 기반 투자 우선순위 판단 가능함

- 향후 예지보전 및 이상 탐지 기능 도입을 위한 데이터 기반 확보 가능함

## 7. 운영 및 데이터 관리 방안

### 7.1 운영 환경

| 항목 | 기준 |
|------|------|
| 운영 방식 | 로컬 PC 또는 사내 로컬 서버 실행 |
| 실행 방식 | `python start.py` 실행 |
| 접속 방식 | 브라우저에서 `http://localhost:5000` 접속 |
| DB | SQLite 파일 기반 |
| 사용자 규모 | 소규모 사용자 환경 권장 |
| 네트워크 | 사내망 또는 제한된 접근 환경 권장 |

### 7.2 데이터 관리 기준

- SQLite DB 파일명은 `mdd_data.db`로 관리함
- 운전일지와 작업 지시서 데이터는 DB에 저장함
- HMI 트렌드와 에너지 사용량은 원본 엑셀 파일을 기준으로 조회함
- 원본 엑셀 파일과 DB 파일은 함께 백업해야 함
- 날짜 기반 파일명 규칙을 준수해야 정상 파싱 가능함

### 7.3 백업 기준

- `mdd_data.db` 파일 정기 백업 필요함
- `HMI_Trend_data/`, `LNG/`, `STEAM/`, `NItrogen/`, `ARGON/`, `Work_Order/` 폴더 백업 필요함
- 신규 파일 반영 후 대시보드 표시 여부 확인 필요함
- 배포 파일 변경 시 `VERSION` 및 `CHANGELOG.md` 업데이트 필요함

## 12. 종합 결론

MDD 프로젝트는 분산된 설비 운영 데이터를 하나의 웹 대시보드로 통합하여 설비 유지보수 업무의 효율성과 데이터 활용도를 높이기 위한 기획임. 초기 버전은 SQLite와 로컬 실행 구조를 기반으로 빠른 도입과 실무 검증을 목표로 하며, 기존 엑셀 기반 업무를 유지하면서도 조회, 집계, 시각화 기능을 개선하는 데 중점을 둠.

향후 데이터가 누적되면 에너지 비용 분석, 설비별 정비 이력 관리, 이상 탐지, 예지보전, 자동 보고서 생성 등으로 확장 가능함. 따라서 MDD는 단순 대시보드가 아니라 기계설비팀의 운영 데이터를 표준화하고, 향후 AI 기반 설비 관리 체계로 발전시키기 위한 기반 시스템으로 정의함.
